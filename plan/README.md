# rtok-net

https://github.com/pyrlyn/rtok-net

rtok rewritten in C# on .NET 10+: a token-reduction CLI for AI coding agents (hooks, MCP
server, API proxy), shipped as NativeAOT binaries and developed on the JIT.

## Where this plan comes from

The plan ports [rtok](https://github.com/pyrlyn/rtok) (at `ef091589`) to .NET. Two inputs:

- rtok's closed work (`done.md`, 1164 tasks). Every behaviour it shipped is a contract the
  port must reproduce. The contracts are listed by area in
  [docs/port/catalog.md](../docs/port/catalog.md).
- rtok's open work (`plan.md`, `todo.md`: 36 tasks, the 2026-10-14 security audit, the
  cloud review). Each item is marked keep, adapt or drop in
  [docs/port/open-work.md](../docs/port/open-work.md).

Each task here has a `Ports:` line naming the rtok ids it covers and the catalog sections
that hold the contracts. Rust-only rtok tasks (toolchain, crate moves, Rust CI) are not
ported; the catalog lists them under "drop".

Library research with sources and measurements: [research.md](../research.md).

## Decisions

N1. **.NET 10 LTS**, SDK 10.0.402 pinned in `global.json` with `rollForward: latestFeature`.
Move to the next LTS when it ships; .NET 11 features (BCL `ZstandardStream`,
`Process.RunAndCaptureTextAsync`) wait for it.

N2. **Release builds are NativeAOT; Debug builds are JIT.** `PublishAot` is set only for
`Configuration=Release` (in `Directory.Build.targets`, where `OutputType` is known). Set
unconditionally, it writes AOT feature switches into `runtimeconfig.json` even for
`dotnet run`, which turns off hot reload and breaks reflection-based code under the JIT.
Libraries set `IsAotCompatible=true`, so the trim and AOT analyzers still run in Debug. A
`DebugAot` configuration gives an AOT-like JIT run when one is needed.

N3. **Fast Debug loop.** In Debug: no analyzers during build (the IDE and CI still run
them), no doc file, `TieredPGO=false`, non-deterministic builds, apphost on, reference
assemblies on, no ReadyToRun. Iterate with `dotnet build --no-restore` and launch
`artifacts/bin/.../rtok` directly. Use `dotnet watch` for the long-running surfaces
(`proxy`, `mcp --http`, `web`). Measured: about 0.5 s per incremental build, 0.06 s to
launch the apphost.

N4. **No Rust code.** Nothing in this repo is written in Rust, links a Rust library or
calls a Rust binary. Native code comes only as C libraries inside NuGet packages (SQLite;
tree-sitter and its grammars).

N5. **NuGet first; own code as its own package.** Use a maintained, AOT-clean NuGet package
when one does the job. When none does, write it under `packages/<Name>/` as a separate
NuGet package with its own README, CHANGELOG, tests and version, marked
`IsAotCompatible`. Generic packages are named `Pyrlyn.*`; rtok's public contracts are named
`Rtok.*`. The list is under "Own packages" below.

N6. **Two binaries.** `rtok-hook` is a tiny AOT client: no SQLite, no ASP.NET Core, no MCP
SDK, no DI container, no Generic Host, STJ source generation only. `rtok` is the full
binary. Measured on macOS arm64: an STJ-only hook starts in about 5 ms; the same code inside
a binary that links Kestrel and the MCP SDK takes about 9 ms before it does any work.

N7. **Store: EF Core + SQLite** (`Microsoft.EntityFrameworkCore.Sqlite`), the creator's
choice. Under AOT it runs with a compiled model and precompiled queries, regenerated at
publish by `Microsoft.EntityFrameworkCore.Tasks`. `Migrate()` does not work under AOT, so
migrations are created with `dotnet ef migrations add`, scripted per migration at build time
and applied by a small embedded runner. All SQL is generated by EF; none is hand-written.
EF never runs in `rtok-hook`. A cold EF process takes about 17 ms against 7.7 ms for plain
Microsoft.Data.Sqlite, so the hook path relies on the resident server (N8). The EF-only rule
covers rtok's own store; another program's database opened read-only may be read with
Microsoft.Data.Sqlite and parameterized SQL (T38).

N8. **Hook latency comes from the resident server.** `rtok hook --serve` keeps the store,
config and plugins warm; `rtok-hook` talks to it over a Unix socket (a named pipe on
Windows). T4 measured it (research.md F): the round trip costs 0.9 ms p50 on Linux and
6.5 ms on macOS, where the process floor alone is 3.2 ms. With a warm EF write it is 3.5 and
8.0 ms.

When the resident is absent, `rtok-hook` prints the host's no-op reply, writes the request
into the resident's 0700 run directory and spawns the resident detached (stdio on
`/dev/null`, new session, no inherited fds, rate-limited by the lock file). The resident
replays queued requests for their writes only (calls row, SessionEnd's `ended_at`); their
reply is already lost, which is fail-open (rtok D1). Measured: 2.0 ms p50 / 3.8 ms p95 on
Linux, 5.7 / 7.9 ms on macOS. The other candidate, running the full hook in place (`execv`
into `rtok hook`), costs 20.2 / 22.5 ms on Linux and 29.6 ms p50 on macOS. That is a cold EF
context (12 to 15 ms over plain SQLite) plus the full binary's 6 to 6.5 ms before `Main`,
which comes from its 14 MB `__DATA` image, not initializers: it has one module initializer.
So the hook path never starts `rtok`, and hook manifests name `rtok-hook` first. This
fallback is provisional for Windows until T52 measures it there.

SQLite: `rtok-hook` links none. For `rtok`, static linking works on macOS and Linux (T4):
- StaticLink.e_sqlite3 2.1.10.1 links on both, and ships Windows `.lib` files too, but its
  prebuilt archives have unverified provenance.
- On Linux, SourceGear.sqlite3 3.53.3's own `libe_sqlite3.a` with SQLitePCLRaw 3 also links.
- On macOS, SourceGear ships only a dylib.

The creator chose (T8): the store uses SQLitePCLRaw 2.1.13's `bundle_e_sqlite3`, the one
Microsoft.EntityFrameworkCore.Sqlite 10.0.13 brings, and `libe_sqlite3` (dylib, so or DLL) ships beside the
binary. Linking it statically into `rtok` is T54.

N9. **CLI parsing: ConsoleAppFramework v5, output: Spectre.Console.** The creator decided
this. ConsoleAppFramework is a source generator: commands are plain methods, options and
help text come from the signature and XML doc comments, and there is no reflection, so the
same code runs under JIT and AOT. Spectre.Console.Cli is not used: it fails at runtime under
AOT. System.CommandLine was the first choice and is dropped.

Measured in a probe (osx-arm64, AOT, 5.7.13 + Spectre.Console 0.57.2): 2.7 MB, about 4.7 ms
for a command or `--help`, zero AOT warnings. Nested commands (`config show`), `-a|--agent`
aliases from doc comments, and raw arguments after `--` (`ConsoleAppContext.EscapedArguments`,
which `rtok run -- <cmd>` needs) all work. The generator fails the build when a doc comment
names a parameter that does not exist.

What ConsoleAppFramework does not give, and how the plan covers it:
- Exit 2 on bad arguments. It exits 1 on a parse error; hooking `ConsoleApp.LogError` to set
  exit code 2 works in the probe. An unknown command prints the root help and exits 0;
  T11 makes it an error with exit 2.
- A command tree at runtime. Man pages, completion scripts and the flag-to-config-key test
  read a command model extracted from the generated `--help` of every command (T12.11),
  checked in and guarded by a drift test.

N10. **Console output: Spectre.Console** for colours, tables, prompts, status and progress.
**TUI: Terminal.Gui v2.** Neither is ever used on hook stdout, MCP, the proxy, `--json` or
pipes.

N11. **Tests: xUnit v3 on Microsoft.Testing.Platform**, with Verify for snapshots, CsCheck
for property tests, WireMock.Net for upstream fakes and NSubstitute for interface mocks.
Tests run on the JIT; only a small AOT test project, which checks that AOT works and uses
no mocks, and smoke tests against the published binaries run AOT, on every OS in CI.
Every task lists the tests that prove it under `Tests:` (project, kind, case); it closes
only when they exist and pass. Verify runs under its OpenSource sponsorship exemption (`Verify_SponsorshipExemption` in
`Directory.Build.props`), renewed yearly and valid only while rtok-net earns no revenue.
Every parser of outside input (host configs, stdin, wire bodies, transcripts, logs, argv)
gets a SharpFuzz target in `tests/Rtok.Fuzz` from the task that lands it, named in that
task's `Fuzz:` line (T53). A target catches only the documented failure type and checks the
code's own invariants; `Rtok.Fuzz.Tests` replays its corpus and generated inputs on every
`dotnet test`, and the `fuzz` build task (`eng/Rtok.Build`) runs it under libFuzzer.

N12. **Plugins are linked statically.** NativeAOT cannot load managed assemblies at
runtime, so a plugin is a project referenced at build time. A build includes or leaves out
a plugin through an MSBuild property; config turns it on or off at runtime. Out-of-tree
plugins build their own `rtok` against `Rtok.Plugin.Sdk`.

N13. **The web dashboard is Blazor WebAssembly.** rtok's React app is not reused; its
pages and UX contracts (catalog A24) are rebuilt as a standalone Blazor WebAssembly app,
`Rtok.Web.Client`. Blazor Server and interactive SSR are not NativeAOT-compatible, so the
host stays Kestrel minimal API + `/ws` in the AOT `rtok`, and serves the client's published
static files (fingerprinted, precompressed) as embedded resources. The `/ws` messages live
once, in C#, in `Rtok.Web.Contracts` with its STJ context, shared by host and client: no
JSON Schema or TypeScript codegen. The UI is built on **Radzen.Blazor** (MIT): layout,
navigation, data grids, dialogs, notifications, charts, sparklines and the light/dark theme;
no hand-rolled widget where a Radzen one fits. ECharts stays only for what RadzenChart
lacks (the graph view), Three.js for the 3D projects overview, both vendored and called
through JS interop; no npm. The costs: a bigger first download than the React bundle
(Radzen adds about 0.45 MB brotli), `'wasm-unsafe-eval'` and
`style-src-attr 'unsafe-inline'` in the CSP (Radzen sets inline style attributes;
`<style>` and scripts stay `'self'`).

N14. **rtok's design rules still apply**, unless a task here says otherwise:
- Hooks fail open: exit 0, unmodified, within 10 ms.
- Everything shortened is recoverable with `expand` (lossless).
- No saving claim without a Measurement row.
- Injections are budgeted and byte-stable.
- PostToolUse only adds context.
- A plugin and its MCP tool ship as one unit (D21). rtok's MCP entry is always written into
  an agent's config (D33).
- Agent hosts' config files change only in rtok's own entry.
- No real agents in tests.
- One logic, one place.

N15. **No compatibility with the Rust rtok store.** The creator decided this. `rtok-net` starts
its own EF Core schema and never reads, migrates or imports a `rtok.db` written by the Rust
rtok. A database it did not create (no `__EFMigrationsHistory`, or a newer migration than it
knows) is refused with a clear message and left untouched.

N16. **The binaries keep their names: `rtok` and `rtok-hook`.** The creator decided this.
rtok-net replaces the Rust rtok and is not installed beside it. On a machine that still has
the Rust store in the home, the N15 refusal message says which file to move away.

N17. **Generic packages are named `Pyrlyn.*` and stay in this repo, under `packages/`, for
now.** The creator decided this. rtok-specific contracts keep the `Rtok.*` prefix. Moving a
package to its own repo is a later decision for the creator.

N18. **PDF uses QuestPDF behind an own abstraction.** The creator decided this. `Rtok.Report`
builds a plain report document model (sections, headings, paragraphs, tables, key-value
rows, code blocks), and each output format is an `IReportRenderer` over that model: md,
html and pdf. QuestPDF is referenced only by `Rtok.Report.Pdf`, which implements that
interface. Nothing else sees a QuestPDF type, so the PDF layer can be rewritten or replaced
without touching the report logic. The project sets the QuestPDF licence type explicitly.

N19. **rtok's flag-gated experiments (catalog A33).** The creator decided these from the
evidence in T51's `done.md`:
- Embeddings beside FTS5: **deferred**. FTS5 is the only memory search; no vector table.
  Reopen as a task, on the `http` provider only, when a bench shows a recall gain over FTS5.
- WASM plugin host: **dropped**. Out-of-tree plugins build their own `rtok` (N12). Runtime
  loading of third-party plugins would be a new decision, not a port.
- Tiered L0/L1/L2 archive context: **deferred**. The archive ships without tiers. Reopen as
  a task behind `plugins.archive.tiers` when a real-session Measurement beats the plain archive.

N20. **Logging: Serilog in `rtok`, nothing in `rtok-hook`.** The creator decided this. Every
log line in `rtok` (CLI, resident `hook --serve`, `mcp`, `proxy`, `web`, demon) goes through
one Serilog pipeline, set up in `Rtok.Log` from the `[log]` section in code (no
`Serilog.Settings.Configuration`: it uses reflection and is not AOT-clean). The rotating file
sink is a small `ILogEventSink` over Pyrlyn.RotatingLog (T12.10), which keeps the catalog's
`.N` files, the `errors.log` copy and lock-safe appends from several processes;
Serilog.Sinks.File is not used, because its size rolling names files `_001` and is not
lock-safe across processes. The `to_db` logs row is another sink, and `RTOK_LOG` debug output
goes to stderr through Serilog.Sinks.Console. Libraries that take an `ILogger` (EF Core,
ASP.NET Core, the MCP SDK) join the same pipeline through Serilog.Extensions.Logging.
`rtok-hook` does not log at all (N6): it passes its lines to the resident, and drops them
when the resident is down.

N21. **Git: LibGit2Sharp, with the `git` CLI for worktrees.** The creator decided this. Repository
reads and ordinary operations (status, diff, log, refs, `HEAD`, tree and blob reads, branch
listing and deletion) go through LibGit2Sharp. `git worktree add|remove|list` runs the `git`
CLI through ProgressRunner (T11), because LibGit2Sharp has no add/remove parity with it. It
ships native libgit2 per RID: the first task that adds it (T40, T24 or T41, whichever lands
first) proves an AOT publish of `rtok` with it: the macOS RIDs natively, the Linux RIDs and
win-x64 in `ci.yml` after the human pushes (this Mac's podman machine does not start) (its `done.md` says which were proven where).
If one fails, it comes back to the creator.
LibGit2Sharp stays out of `rtok-hook` and the hook path.

An architecture test keeps the layers from rtok: surfaces → app → core → foundation →
`Rtok.Plugin.Sdk`. Nothing references upward. Only surfaces write to the console.

## Parallel lanes

Nine agents work the plan at once, one lane each, in this order: blockers and the most complex
tasks first. T1 is done. A task whose dependency (another lane's task) has no `done.md` on
`main` yet waits: take the next task in your lane whose dependencies are met, and come back.
Never take a task from another lane. Shared files (`Directory.Packages.props`, `rtok.slnx`)
conflict on rebase: keep both sides.

| Lane | Area | Order |
| --- | --- | --- |
| L1 | tests, plugin contract, core, cmd/memory plugins | T2, T5, T6, T53, T17, T17.1, T18, T22, T23, T22.1 |
| L2 | store, archive, logs, proxy | T8, T10, T9, T27, T29, T28, T54, T50 |
| L3 | packages layout, config, CLI shell, operator web and TUI | T12, T12.9, T7, T12.6, T11, T43, T44, T44.2, T45 |
| L4 | hook latency, hooks, resident, MCP, agents | T4, T13, T14, T15, T16, T37, T46, T49, T44.1, T52 |
| L5 | tree-sitter, read, graph, Windows | T12.5, T24, T19, T25, T26, T24.1, T48 |
| L6 | file kit, JSONC, MCP install, hosts, doctor | T12.1, T12.3, T34, T35, T32, T35.3, T35.5, T35.4, T35.6, T35.2, T35.1 |
